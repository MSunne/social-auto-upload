# Codex 高效开发 SOP

## 1. 适用范围

- 适用于本仓库的日常 `bug` 修复、功能开发、小型重构和接口联调。
- 适用于使用 `Codex` 辅助开发，但希望避免上下文噪音、工作区污染和响应变慢的场景。

## 2. 先记住这 6 条

1. 新线程是对的，但新线程不等于新环境。
2. 每个任务尽量使用单独 `worktree`，不要把多个任务堆在同一个工作区。
3. 让 `Codex` 只看到当前任务需要的最小目录。
4. 一次只启动当前任务需要的服务。
5. 提示词要写成“工单”，不要写成“闲聊”。
6. 一个任务结束就提交，不要把未提交改动堆一整天。

## 3. 为什么你会感觉越来越慢

- `Codex` 变慢，很多时候不是模型问题，而是当前工作区太脏。
- 同一个仓库里混着多个子项目、多个前端依赖、构建缓存、日志和未提交改动时，检索和判断成本会显著升高。
- 如果同时跑多个 `dev server`、`tsserver`、浏览器自动化进程，系统内存和文件监听压力也会明显上升。
- 只开新线程，但继续复用同一个大工作区，本质上只是换了聊天记录，没有换上下文负担。

## 4. 标准工作流

### 4.1 一个任务一个 worktree

1. 在仓库根目录创建新工作树和新分支。
2. 进入该工作树后，再决定是在根目录还是更小的子目录里启动 `Codex`。
3. 任务完成后提交代码。
4. 合并回主分支后删除该 `worktree`。

常用命令：

```bash
cd /Volumes/mud/project/github/social-auto-upload

git worktree add ../sau-bug-upload-timeout -b codex/bug-upload-timeout
git worktree list
git worktree remove ../sau-bug-upload-timeout
git branch -d codex/bug-upload-timeout
```

### 4.2 在最小目录启动 Codex

按任务类型选择目录：

- 修 `Flask` 后端或跨模块逻辑：在 `worktree` 根目录启动。
- 修 `Vue` 前端：在 `sau_frontend` 启动。
- 修某个平台上传器：在对应 `uploader/<platform>_uploader` 附近启动。
- 只改工具脚本：在 `scripts` 或相关目录启动。

建议：

- 前端单点问题，不要让 `Codex` 扫描整仓库。
- 纯后端问题，不要顺手带上前端目录和其他子项目。
- 只有确实跨前后端联动时，才在 `worktree` 根目录启动。

### 4.3 如果桌面端不能多开窗口

- 这不影响使用 `worktree`。
- 正确做法是先切到目标目录，再启动一个新的 `Codex` 会话。
- 重点不是多开几个窗口，而是当前会话的工作目录要足够小。

## 5. Bug 修复 SOP

### 5.1 开始前先准备 4 件事

1. 明确复现步骤。
2. 明确期望结果和实际结果。
3. 指定改动范围。
4. 指定完成后的验证方式。

### 5.2 适合直接发给 Codex 的 bug 提示词

```text
直接修，不要只分析。

问题：
[一句话描述问题]

复现步骤：
1. ...
2. ...
3. ...

期望结果：
- ...

实际结果：
- ...

限制：
- 只改后端 / 只改前端 / 只改 uploader
- 不改接口协议
- 优先最小修复

完成要求：
- 解释根因
- 直接改代码
- 跑相关验证或给出最小验证步骤
```

### 5.3 Bug 处理时的拆分原则

- 先做最小修复，不要顺手重构无关代码。
- 如果问题跨多个模块，先确认真正根因，不要见到异常就全链路改一遍。
- 优先要求 `Codex` 解释根因，再看修改是否必要和最小。
- 如果复现路径复杂，先让 `Codex` 补充最小日志点或断言，再改逻辑。

### 5.4 Bug 结束前检查

1. 是否真的复现过问题。
2. 是否只改了与问题相关的代码。
3. 是否做了最小验证。
4. 是否写清楚了根因。
5. 是否把无关改动排除在本次提交之外。

## 6. 新功能 SOP

### 6.1 新功能开始前必须先定范围

至少说明这 5 项：

1. 目标是什么。
2. 包含哪些内容。
3. 不包含哪些内容。
4. 数据来源或接口来源是什么。
5. 验收标准是什么。

### 6.2 适合直接发给 Codex 的新功能提示词

```text
直接实现，不要先写大方案。

目标：
- ...

范围：
- 包含 ...
- 不包含 ...

数据来源：
- 使用现有接口 ...
- 如果没有，再补最小后端接口

约束：
- 保持现有风格
- 不做额外重构
- 优先最小可用实现

验收标准：
- 页面/接口可以做到 ...
- 空状态正常
- 错误状态正常

完成要求：
- 直接改代码
- 补最少必要测试
- 告诉我改了什么
```

### 6.3 新功能的正确拆法

- 先做 `MVP`，再做体验优化。
- 优先拆成“数据层、接口层、展示层”三个独立问题。
- 每一轮只完成一个明确的验收目标。
- 如果功能跨度大，拆成多个 `worktree` 也比在一个分支里堆着更稳。

### 6.4 新功能结束前检查

1. 是否满足最初验收标准。
2. 是否引入了额外的接口或状态复杂度。
3. 是否补了最低限度的验证。
4. 是否顺手改乱了无关页面或模块。

## 7. 提示词技巧

### 7.1 高效提示词的特征

- 有明确目标。
- 有明确边界。
- 有明确限制。
- 有明确验收标准。
- 明确让 `Codex` 直接改代码，而不是只分析。

### 7.2 低效提示词的典型写法

- “帮我看看这里为什么不对。”
- “这个功能怎么做比较好。”
- “顺便优化一下。”
- “你先分析。”

这些问题会让 `Codex` 在大范围里猜背景、猜范围、猜你的真实诉求，速度会明显下降。

### 7.3 推荐加上的限制语

- “只改这个模块。”
- “不要改接口协议。”
- “先做最小修复。”
- “不要做额外重构。”
- “如果需要扩大范围，先说明原因。”

## 8. 提速技巧

### 8.1 目录和工作区

- 不要长期在一个脏工作区里连续做多个任务。
- 不要让一个 `worktree` 同时承载 `bug`、功能、重构三类任务。
- 前端问题尽量在 `sau_frontend` 目录启动会话。
- 后端问题尽量不要让 `Codex` 扫描无关前端依赖和构建目录。

### 8.2 运行时环境

- 一次只开一个必要的前端服务。
- 不用的 `next dev`、`vite`、`python` 服务及时关闭。
- 浏览器自动化或抓取流程不用时，不要一直挂着。
- 系统开始频繁交换内存时，优先关服务，而不是硬撑。

### 8.3 Git 习惯

- 一个任务一个分支。
- 一个分支一个明确目的。
- 一个目的完成就提交。
- 不要把十几个文件的无关改动混成一个提交。
- 发现工作树脏了，优先隔离任务，不要继续硬做。

### 8.4 线程使用

- 新线程适合隔离聊天历史。
- `worktree` 适合隔离代码上下文。
- 两者配合使用才是真的快。
- 长线程适合单任务持续推进，不适合跨多个任务反复跳转。

## 9. 仓库内推荐的目录选择

### 9.1 修 `sau_frontend` 页面或状态问题

- 启动目录：`sau_frontend`
- 典型命令：

```bash
cd /Volumes/mud/project/github/social-auto-upload
git worktree add ../sau-fe-task-center -b codex/fe-task-center
cd ../sau-fe-task-center/sau_frontend
```

### 9.2 修 `Flask` 后端、上传编排、数据库逻辑

- 启动目录：`worktree` 根目录
- 典型命令：

```bash
cd /Volumes/mud/project/github/social-auto-upload
git worktree add ../sau-bug-db-task -b codex/bug-db-task
cd ../sau-bug-db-task
```

### 9.3 修某个平台上传器

- 启动目录：`worktree` 根目录或对应 `uploader` 子目录
- 常见目标：
  - `uploader/douyin_uploader`
  - `uploader/bilibili_uploader`
  - `uploader/tencent_uploader`

## 10. 每日开发建议流程

1. 先明确今天只做哪一个任务。
2. 创建对应 `worktree`。
3. 切到最小目录启动 `Codex`。
4. 只打开当前任务需要的服务。
5. 用标准提示词发起任务。
6. 修改后立即做最小验证。
7. 验证通过就提交。
8. 任务结束后关闭服务，必要时删除 `worktree`。

## 11. 常见反模式

- 在同一个目录里连做多个不相关任务。
- 在同一个分支里堆一整天修改。
- 同时开多个前端开发服务但只用其中一个。
- 提示词不给复现步骤和验收标准。
- 让 `Codex` 在整个大仓库里猜你的意图。
- 一边修 bug，一边顺手做重构和新功能。

## 12. 一个最小可执行示例

目标：修 `sau_frontend` 的发布页 bug。

```bash
cd /Volumes/mud/project/github/social-auto-upload
git worktree add ../sau-bug-publish-page -b codex/bug-publish-page
cd ../sau-bug-publish-page/sau_frontend
npm install
npm run dev
```

发给 `Codex`：

```text
直接修，不要只分析。

问题：
发布页点击提交后没有任何反馈。

复现步骤：
1. 打开发布页
2. 选择一个视频
3. 点击提交

期望结果：
- 显示提交中状态
- 成功后提示成功

实际结果：
- 页面无响应

限制：
- 只改 sau_frontend
- 不改后端接口
- 优先最小修复

完成要求：
- 解释根因
- 直接改代码
- 给出最小验证步骤
```

任务做完后：

```bash
git status
git add .
git commit -m "fix: repair publish page submit feedback"
```

## 13. 结论

- 高效率不是靠更长的线程，而是靠更小的上下文。
- 最有效的组合是：`新 worktree + 最小目录 + 精确提示词 + 单任务提交`。
- 如果你感觉 `Codex` 又开始慢了，先看工作区是否变脏，再看是否同时开了太多服务，最后再怀疑模型。
